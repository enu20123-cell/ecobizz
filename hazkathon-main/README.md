# EcoBiz Copilot

Рабочий MVP для трека **EcoFin** хакатона Future Minds Hackathon 2026. Сервис
анализирует ежедневное потребление ресурсов (электричество, вода, тепло)
школой или малым бизнесом, находит периоды, когда здание продолжало их
расходовать во время простоя, и переводит это в конкретную цифру экономии в
тенге и CO₂ плюс рекомендацию на понятном языке.

## Что отличает этот проект

- **Детекция с учётом погоды** — расход на отопление в мороз в нерабочий
  день сравнивается не с одним общим порогом, а с ожиданием для *этой самой*
  температуры (линейная регрессия по градусо-дням отопления), так что
  легитимный обогрев не путается с забытым включённым оборудованием.
- **Мультиресурсность** — та же самая, ничем не отличающаяся статистика
  (25-й перцентиль нерабочих дней × порог) независимо применяется к
  электричеству, воде и теплу, если они есть в файле.
- **Честный ИИ** — на вкладке AI-рекомендаций видно ровно те цифры, которые
  ушли в промпт Gemini; модель ничего не придумывает и не получает сырых
  данных сверх уже проверенного расчёта.
- **Доставка результата в Telegram** — не только веб-дашборд: `/demo` или
  присланный файл в боте дают тот же результат без визита на сайт.

## Что делает MVP

- принимает CSV/XLSX с колонками `date` и `consumption_kwh` (опционально
  `is_workday`, `water_m3`, `heat_gcal`);
- если колонки `is_workday` нет, определяет её сама по выходным дням плюс
  государственным праздникам и школьным каникулам Казахстана
  (`holidays_kz.json`) — расписание, предоставленное школой, всегда имеет
  приоритет над автоматическим определением по календарю;
- находит аномалии через нижний квартиль потребления в нерабочие дни, для
  каждого ресурса (`consumption_kwh`, `water_m3`, `heat_gcal`) независимо;
- по запросу (`weather_adjust=true`) сравнивает электропотребление не с
  плоским порогом, а с ожиданием, рассчитанным по исторической температуре
  Астаны (Open-Meteo) — см. «Погодная поправка» ниже;
- показывает избыточные единицы ресурса, потенциальную экономию в тенге и
  (где это физически осмысленно) предотвращённые выбросы CO₂;
- явно отмечает, когда сама база слишком мала, чтобы ей доверять
  (`baseline_reliable`);
- обращается к Gemini за планом действий на понятном языке, но всегда
  продолжает работать без ключа или интернета благодаря локальному
  запасному варианту рекомендации;
- показывает интерактивный дашборд (графики, таблица аномалий, переключатель
  ресурса, панель AI Copilot) прямо из FastAPI-бэкенда;
- отвечает тем же анализом в Telegram через `bot.py` — `/demo` для мгновенного
  примера или присланный файл.

## Структура проекта

```text
backend/
  main.py            # FastAPI-приложение: /api/analyze, /api/insight, /api/health
  ai.py               # клиент Gemini (выбрасывает AIUnavailable без ключа/сети/при ошибке)
  schemas.py          # контракт запросов/ответов на Pydantic
core.py               # загрузка/очистка данных, детекция аномалий (в т.ч. с погодной поправкой), расчёт экономии
calendar_utils.py     # выходные + праздники/каникулы -> is_workday
weather.py             # историческая температура Астаны (Open-Meteo) для погодной поправки
holidays_kz.json      # календарь государственных праздников и каникул РК
config.py             # заметки по источникам тарифа/CO2 по каждому ресурсу, которые команда должна перепроверить
bot.py                 # Telegram-бот — отдельный процесс, вызывает тот же backend
frontend/              # статический дашборд (обычные HTML/CSS/JS, без сборки)
data/
  sample_data.csv       # встроенный демо-датасет, только электричество (декабрь, аномалия на неделе каникул)
  sample_data_multi.csv # тот же месяц + синтетические вода/тепло, для демонстрации мультиресурсности
  generate_sample.py    # пересоздаёт оба демо-датасета
tests/                # набор тестов pytest (основная логика, календарь, контракт API, бот)
scripts/run.sh        # запуск venv + uvicorn
```

## Быстрый старт

Нужен Python 3.10+.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate   |   macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
uvicorn backend.main:app --reload
```

Открой `http://127.0.0.1:8000` для дашборда, либо `http://127.0.0.1:8000/docs`
для интерактивной документации FastAPI (удобно для демонстрации `/api/analyze`
без кода, на файле `data/sample_data.csv`).

```bash
curl http://127.0.0.1:8000/api/health
```

## API

**`POST /api/analyze`** — `multipart/form-data`, `file` опционален (при
отсутствии используется встроенный демо-датасет). Query-параметры:
`tariff` (тенге/кВт·ч, только для электричества), `multiplier` (порог
аномалии, по умолчанию 1.5), `weather_adjust` (`true`/`false`, по умолчанию
`false` — см. «Погодная поправка» ниже), `sample` (`default`/`multi`, какой
встроенный демо-файл использовать, если `file` не передан). Возвращает
`summary`/`series` для электричества (как раньше, без изменений), плюс
`weather_adjusted` (реально ли применилась погодная поправка) и `resources`
— словарь по каждому ресурсу, найденному в файле (`electricity`, и, если
есть колонки, `water`/`heat`), с той же формой данных (базовый уровень,
аномалии, экономия, дневной ряд), что и `summary`/`series`.

**`POST /api/insight`** — принимает `summary`/`series` из `/api/analyze` и
возвращает план действий в формате Markdown. Использует Gemini, если задан и
доступен `GEMINI_API_KEY`; в противном случае возвращает локально
сгенерированную рекомендацию на основе тех же проверенных цифр (`model:
"offline-fallback"` в ответе), чтобы демонстрация никогда не зависела от
Wi-Fi.

**`GET /api/health`** — проверка работоспособности.

### Минимальный формат входных данных

```csv
date,consumption_kwh
2026-03-19,420.5
2026-03-20,410.2
```

### С точным расписанием школы и другими ресурсами

```csv
date,consumption_kwh,water_m3,heat_gcal,is_workday
2026-03-19,420.5,11.2,3.1,0
2026-03-20,410.2,10.8,3.3,0
```

`water_m3` и `heat_gcal` полностью опциональны — файл без них ведёт себя
ровно как раньше. `is_workday=1` — обычный рабочий день, `0` — нерабочий.
Если строка пропущена, некорректна или содержит отрицательное значение,
`/api/analyze` вернёт `422` с конкретным сообщением вместо того, чтобы
незаметно исказить результат.

## Как работает детекция

1. Берутся только нерабочие дни (из файла либо автоматически определённые по
   календарю РК).
2. Базовый уровень = 25-й перцентиль их потребления — устойчив к тем самым
   выбросам, которые мы пытаемся найти, в отличие от обычного среднего.
3. День считается аномалией, если `consumption_kwh > базовый уровень x 1.5`.
4. Превышение в аномальный день: `фактическое значение - базовый уровень`.
5. Экономия: `превышение x тариф`; предотвращённый CO₂: `превышение x
   коэффициент CO2`.

Это статистическое обнаружение аномалий во временном ряде, а не нейросеть —
осознанный выбор для MVP: метод честный, объяснимый на Q&A и достаточный для
такого объёма данных. `baseline_reliable` равен `False`, если доступно
меньше 5 нерабочих дней; результат всё равно показывается, но не должен
преподноситься как подтверждённый факт.

Gemini решает другую, отдельную задачу: превращает уже проверенные цифры в
короткий план действий для нетехнического управляющего зданием. Каждое
число и дата в рекомендации берутся из расчёта, модель их не придумывает.

Электричество, вода и тепло детектируются каждое по этой же самой логике,
независимо друг от друга — просто на разных колонках (`consumption_kwh`,
`water_m3`, `heat_gcal`). Если файл содержит только `consumption_kwh`,
поведение полностью совпадает с версией без мультиресурсности.

## Погодная поправка (`weather_adjust=true`)

Плоский порог не отличает «здание забыли выключить» от «в мороз отопление
законно поработало чуть сильнее». При `weather_adjust=true` `/api/analyze`:

1. запрашивает историческую среднесуточную температуру Астаны за диапазон
   дат файла через Open-Meteo (`weather.py`, без ключа);
2. переводит её в градусо-дни отопления: `HDD = max(0, 18°C - средняя_температура)`;
3. строит линейную регрессию `ожидаемое_потребление = intercept + slope × HDD`
   по нерабочим дням (`numpy.polyfit`);
4. аномалия — превышение *своего* ожидания для HDD конкретного дня, а не
   одного общего числа на весь набор данных.

Если Open-Meteo недоступен (нет интернета, сбой сервиса) или данных слишком
мало, чтобы построить осмысленную линию, всё автоматически откатывается на
обычный плоский базовый уровень без ошибки — поле `weather_adjusted` в
ответе показывает, что именно сработало. По умолчанию (`weather_adjust`
не передан) поведение `/api/analyze` не меняется вовсе — фронтенд и бот
запрашивают погодную поправку явно.

## Тарифы и CO2 — честное ограничение

Тариф по умолчанию (17.447 тенге/кВт·ч) — реальный бытовой тариф Абайской
области, указанный в брифе проекта, **но не** подтверждённая ставка для
конкретной школы или бизнеса. `config.py` документирует это, а также
альтернативные региональные тарифы с источниками; подтвердите реальный
договорной тариф перед предъявлением финальных цифр и передавайте его через
параметр `tariff`. Коэффициент CO2 по умолчанию (0.85 кг/кВт·ч) — также
демонстрационное допущение до подтверждения методологии — см.
`config.CO2_FACTOR_TODO`.

Тарифы на воду и тепло (`config.WATER_TARIFF_KZT_PER_M3_DEMO`,
`config.HEAT_TARIFF_KZT_PER_GCAL_DEMO`) — **демо-значения**, не привязанные
к конкретному поставщику; как и электричество, подтвердите их перед финальной
подачей. Для воды CO2 намеренно не считается (`co2_saved_kg: null` в
ответе) — водоснабжение не имеет для этого прямого физического обоснования,
в отличие от электричества и отопления.

## Настройка Gemini

1. Скопируйте `.env.example` в `.env`.
2. Впишите `GEMINI_API_KEY`.
3. Никогда не коммитьте `.env`.

Без ключа, без сети или при ошибке Gemini `/api/insight` автоматически
возвращает офлайн-рекомендацию — демонстрация не зависит от Wi-Fi.

## Telegram-бот

`bot.py` — отдельный процесс, не часть FastAPI-приложения; он обращается к
тому же backend по HTTP (`/api/analyze`, `/api/insight`), так что логика
анализа существует только в одном месте.

1. Скопируйте `.env.example` в `.env`, впишите `TELEGRAM_BOT_TOKEN` (токен
   от [@BotFather](https://t.me/BotFather)).
2. Запустите backend: `uvicorn backend.main:app`.
3. В другом терминале: `python bot.py`.

`/start` объясняет, что умеет бот; `/demo` — мгновенный анализ встроенного
примера без файла (удобно для сцены); присланный `.csv`/`.xlsx`/`.xls`
анализируется тем же способом, что и в веб-дашборде, с ответом сводкой цифр
и планом действий от Gemini (или офлайн-заменой).

## Подготовка к Q&A: что должен уметь объяснить каждый участник команды

**Данные и статистическое ядро**

- *Почему 25-й перцентиль, а не среднее?* Среднее может быть завышено теми
  же аномалиями, которые мы пытаемся найти; 25-й перцентиль остаётся ближе к
  корректно выключенному зданию.
- *Почему порог 1.5x?* Простой, объяснимый порог для MVP — потребление
  должно быть явно выше базового уровня, а не немного превышать его. Может
  стать настраиваемым параметром, когда накопится больше реальной истории
  для калибровки.
- *Почему `baseline_reliable` может быть false?* При 1-4 нерабочих днях
  нельзя честно утверждать норму. Код всё равно показывает предварительный
  сигнал, но не скрывает слабость данных.
- *Что происходит, если `is_workday` отсутствует?* Определяется по выходным
  плюс `holidays_kz.json` (государственные праздники Казахстана и типичные
  школьные каникулы, источник — gov.kz). Колонка, заданная вручную, всегда
  имеет приоритет.
- *Почему погодная поправка — это регрессия, а не ещё один множитель?*
  Множитель одинаково относится ко всем нерабочим дням; связь между
  температурой и отоплением не линейная константа, а линия — регрессия даёт
  для каждой температуры своё ожидание, множитель на это не способен.
- *Что если данных для регрессии мало или Open-Meteo недоступен?*
  `detect_anomalies_weather_adjusted` возвращает `None`, и код откатывается
  на обычный плоский базовый уровень — тот же путь, что работал раньше;
  `weather_adjusted: false` в ответе честно об этом сообщает.
- *Почему вода и тепло используют ту же функцию `detect_anomalies`, а не
  отдельный алгоритм?* Потому что статистика не зависит от единицы измерения
  — 25-й перцентиль нерабочих дней и порог `× 1.5` работают одинаково для
  кВт·ч, м³ и Гкал; `value_column` просто указывает, какую колонку читать.

**Gemini и API**

- *Зачем нужна LLM, если формула и так работает?* Формула находит проблему;
  LLM переводит её в действие, понятное нетехническому человеку. Это
  отдельная функция, а не "чат ради чата".
- *Как вы не даёте Gemini придумывать цифры?* В промпт передаются только
  проверенные значения из `impact`/`summary`, и те же цифры дублируются в
  ответе самим приложением — задача модели — изложение, а не арифметика.
- *Что происходит без интернета?* `/api/insight` никогда не вернёт `503` по
  этой причине — он возвращает шаблонную рекомендацию, построенную на тех же
  проверенных цифрах.
- *Почему CORS полностью открыт?* Только для удобства локальной разработки;
  перед любым публичным развёртыванием разрешённый origin будет ограничен
  доменом приложения.

Перед защитой каждый участник команды должен запустить проект локально,
прочитать раздел "Как работает детекция" выше и быть готовым ответить на эти
вопросы своими словами — по правилам AI-политики хакатона, неспособность
объяснить фрагмент кода обнуляет баллы за техническую защиту по этому
фрагменту.
